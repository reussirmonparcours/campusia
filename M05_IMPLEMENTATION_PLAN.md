# MONPARCOURS — M05 AI INTERFACE

## 1. Objective
Créer une couche d'abstraction robuste (AI Interface Layer) permettant l'intégration future de modèles LLM dans MonParcours sans créer un couplage fort avec un fournisseur (ex: OpenAI) et en garantissant une injection intelligente du contexte étudiant, pédagogique et académique. 

## 2. Product Scope
L'IA dans MonParcours n'est pas un chatbot isolé, mais une extension contextuelle de l'expérience d'apprentissage. Le périmètre de M05 couvre la création des contrats (Requests/Responses), la construction du contexte (Context Builder), la définition des modes pédagogiques et le modèle de sécurité. Ce jalon n'inclut **pas** l'appel réel à un LLM, la logique RAG (M09/M10), ou les moteurs de révision complexes (M06).

## 3. AI Architecture
L'architecture de flux sera la suivante :
Client (UI) → Next.js Route Handler / Server Action (Auth/Validation) → AI Interface Layer → Context Builder → AI Request (Contrat structuré) → AI Provider Adapter (Mock Provider en M05) → AI Response (Contrat structuré) → UI.
Le fournisseur (Provider) implémentera une interface commune `AIProvider` (ex: `generate(request)`, `stream(request)`).

## 4. AI Context Model
Le contexte sera composé de :
- **Student Context** : Semestre, parcours, niveau.
- **Academic Context** : Infos officielles sur la matière/programme actuel.
- **Learning Context** : Historique (MAX 5 activités M03 récentes pertinentes, MAX 5 erreurs/tentatives M04 pertinentes). Filtrage dynamique par `subjectId` si fourni, sinon sélection globale priorisée.
- **Current Context** : Page active, exercice en cours, question bloquante.
- **Source Context** : Textes académiques injectables plus tard par RAG.

## 5. Provenance Model
Distinguer formellement deux concepts pour éviter les hallucinations :
**A. SOURCE PROVENANCE (La source de la donnée)**
- `OFFICIAL` : Catalogue ou cours officiels (fiabilité haute).
- `STUDENT` : Notes personnelles ou documents de l'étudiant.
- `SYSTEM` : Statistiques issues de MonParcours.
**B. GENERATED BY (Le générateur)**
- `AI` : La réponse en elle-même est générée par l'IA.
Une réponse IA ne devient JAMAIS une source académique. Exemple : `OFFICIAL` source → `AI`-generated explanation. Toute source retournée à l'UI portera son tag de provenance d'origine.

## 6. AI Modes
L'architecture supportera via un champ `mode` dans la requête :
- `explain` : Expliciter un concept ou une erreur.
- `summarize` : Synthétiser une matière.
- `quiz` / `exercise` : Générer une question dynamique.
- `coach` : Conseiller sur les objectifs.
La logique de ces modes sera gérée côté "Prompt Builder" ou "Future Engine", M05 prépare juste l'aiguillage.

## 7. AI Request Contract
Contrat Zod strict côté serveur (non exposé tel quel au client) :
```typescript
interface AIRequest {
  mode: 'explain' | 'summarize' | 'quiz' | 'coach';
  studentContext: StudentContext; // sanitized (no PII)
  learningContext?: LearningContextSummary;
  sourceContext?: SourceDocument[]; // DTO interne (le source_id n'est pas envoyé au LLM)
  currentContext?: CurrentState;
  userMessage: string;
}
```

## 8. AI Response Contract
Contrat de sortie structuré pour le frontend :
```typescript
interface AIResponse {
  message: string;
  mode: string;
  generatedBy: 'AI';
  sourceProvenance: ProvenanceTag[]; // citations from OFFICIAL, STUDENT, SYSTEM
  suggestedActions?: UIAction[]; // e.g., "Aller à l'exercice X"
  warnings?: string[];
}
```

## 9. Source-Grounded Behavior
Instructions système définies dans l'interface :
Si aucune `OFFICIAL` source n'est jointe au contexte pour une requête nécessitant une vérité académique locale (ex: "Quelles sont les modalités d'examen de FASEG ?"), l'IA doit avoir une instruction stricte de répondre qu'elle manque d'informations et refuser de deviner. L'IA n'est jamais une source de vérité, elle explique une source. Le RAG M09/M10 viendra alimenter ce canal de sources.

## 10. Conversation / Session Model
**Décision** : **M05 IMPLÉMENTE réellement deux tables `ai_sessions` et `ai_messages`.**
Bien que le contexte de fond soit dynamiquement recalculé, le fil de la discussion (chat) doit pouvoir persister pour ne pas briser l'historique conversationnel de l'utilisateur si ce dernier navigue ou rafraîchit.
- L'historique académique n'est **pas** dupliqué dans `ai_messages`.
- Seuls le prompt utilisateur et la réponse IA sont persistés.

**RLS - Règles minimales :**
- `ai_sessions` : SELECT uniquement pour le propriétaire ; INSERT uniquement pour `auth.uid()` ; UPDATE/DELETE uniquement pour le propriétaire.
- `ai_messages` : Accès (SELECT) uniquement si la session appartient à `auth.uid()` ; impossible de lire les messages d'une session d'un autre utilisateur ; impossible d'insérer un message dans la session d'un autre utilisateur.

## 11. Provider Abstraction
Interface `AIProvider` :
- `generate(request: AIRequest): Promise<AIResponse>`
- `stream(request: AIRequest): AsyncIterable<Partial<AIResponse>>`
En M05, création d'un `MockAIProvider` sans aucun LLM, implémentant exactement les modes (`explain`, `summarize`, `quiz`, `coach`) et respectant strictement les contrats `AIRequest` et `AIResponse` pour valider l'UX.

## 12. Prompt Architecture
L'assemblage des Prompts utilisera un pattern de Builder :
1. **System Policy** (Règles globales de sécurité, tone of voice, format JSON/Structuré)
2. **Mode Instructions** (Ex: Tu es un coach, ton but est...)
3. **Data Blocks** (Contexte académique, learning, sources encapsulées dans des balises xml : `<context>...</context>`)
4. **User Input** (Requête directe)
Séparation claire des Data et des Instructions pour mitiger les injections.

## 13. Security & Privacy
- **Privacy** : Exclusion TOTALE et PAR DÉFAUT des informations personnelles (PII). Le `ContextBuilder` n'envoie ni nom, ni prénom, ni pseudonyme, ni email, ni téléphone, ni UUID interne. Seules les données académiques et pédagogiques utiles au LLM sont transmises.
- **Sécurité** : L'API LLM n'est jamais appelée par le client. Tout passe par le Backend. Validation Zod en entrée. Rate limiting implémenté via des tokens ou timestamps. 

## 14. Prompt Injection Protection
Les balises XML servent uniquement à STRUCTURER et délimiter les données. Elles **ne constituent PAS** une garantie absolue contre l'injection de prompts.
Toutes les données provenant de documents étudiants, de messages utilisateurs ou de sources externes sont considérées comme des **UNTRUSTED DATA**. 
Ces données ne doivent jamais pouvoir redéfinir la System Policy, les Mode Instructions, le format de sortie ou les règles de sécurité.
Le modèle doit explicitement séparer les **INSTRUCTIONS DE CONFIANCE** des **DONNÉES NON FIABLES**. 
(Pas de système anti-injection excessivement complexe codé dans M05, mais l'architecture prévient conceptuellement ces failles).

## 15. Error Handling
Des codes d'erreurs standardisés (`PROVIDER_UNAVAILABLE`, `CONTEXT_TOO_LARGE`, `RATE_LIMIT_EXCEEDED`, `UNSAFE_CONTENT`). Le client reçoit une UI gracieuse ("L'assistant est indisponible pour le moment") sans fuite de stack trace ou d'API key.

## 16. Observability
Les requêtes via le `AIProvider` loggueront (sans le contenu sensible des messages) :
- ID Session, Provider utilisé, Mode, Tokens utilisés (futur), Temps de réponse.
Cela permet de surveiller l'usage et les coûts indépendamment du contenu pédagogique privé.

## 17. M03/M04 Integration
Le `ContextBuilder` interrogera intelligemment :
- M03 : Au maximum 5 activités récentes depuis `student_activities`.
- M04 : Au maximum 5 erreurs ou tentatives pertinentes récentes.
Ces données sont filtrées par pertinence (privilégiant le `subject_id` en cours si disponible, sinon les données globales récentes les plus importantes) pour maintenir un contexte compact.
Un module `buildStudentLearningContext(userId, subjectId?)` sera conçu pour renvoyer cette synthèse filtrée.

## 18. Open Mode
Le contexte n'assumera jamais que la matière est "FASEG". Le `ContextBuilder` extrait simplement le nom de la matière et la description liée au `subject_id` en cours, qu'il soit officiel ou privé.

## 19. Future RAG Compatibility
Le `SourceContext` interne dans le contrat backend accepte un tableau d'objets : `{ content: string, source_id: string, provenance: 'OFFICIAL' | 'STUDENT' }`. 
**Règle stricte (Privacy / RAG)** : Le `source_id` est souvent un UUID ou un identifiant interne de base de données. Il ne doit **JAMAIS** être transmis au provider/LLM. Le contexte envoyé au provider (payload) contiendra uniquement le `content`, la `provenance`, et éventuellement un `source_label` non sensible (ex: "Document 1"). Le backend conservera séparément le mapping entre la vraie source (`source_id`) et son label envoyé au modèle pour garantir la traçabilité des citations dans l'UI sans fuite d'identifiants internes. M09 viendra brancher sa base vectorielle sur cette mécanique transparente.

## 20. UX / Routes
- **Boutons contextuels** : Un bouton "Comprendre mon erreur" sur la page de Résultat M04 qui ouvre un side-panel IA.
- **Espace dédié** : `/dashboard/ai/[sessionId]` pour une conversation continue avec un coach général.
- Composant global (ex: `AIChatSheet`) accessible contextuellement sans perdre la page de cours.

## 21. Database Decision
M05 implémente concrètement deux nouvelles tables avec RLS strict :
- `ai_sessions` : id, user_id, mode, subject_id (optionnel), created_at.
- `ai_messages` : id, session_id, role (user/assistant), content, sources_used (jsonb), created_at.

## 22. Testing Strategy
- Tests unitaires du `ContextBuilder` (vérifier que les données PII sont filtrées).
- Tests de l'abstraction `AIProvider` en utilisant le `MockAIProvider`.
- Tests de la UI avec des réponses simulées streamées.

## 23. Roadmap Compatibility
Parfaite isolation. Prépare le terrain pour que M06 (Revision) puisse s'appuyer sur l'interface pour générer des QCM. Compatible M10 car OpenAIProvider implémentera simplement l'interface `AIProvider`.

## 24. Risks & Trade-offs
- *Risque* : Le contexte s'alourdit vite avec l'historique M03.
- *Trade-off* : Le `ContextBuilder` limitera drastiquement à MAX 5 activités + MAX 5 erreurs avec un filtrage intelligent par pertinence (`subject_id`).
- *Risque* : Hallucinations sur du contenu officiel FASEG.
- *Trade-off* : Strictement contraint par le System Prompt (Source-Grounded) pour répondre "Je ne sais pas".

## 25. Definition of Done
Le M05 sera terminé quand :
1. L'abstraction `AIProvider` et ses contrats Zod sont codés.
2. Les tables `ai_sessions` et `ai_messages` sont opérationnelles avec RLS fonctionnel et testé.
3. Le `ContextBuilder` assemble correctement un contexte (avec PII minimisée et filtrage pertinent).
4. Le modèle de provenance distingue proprement SOURCE PROVENANCE et GENERATED BY.
5. Le `MockAIProvider` répond fidèlement aux 4 modes sans LLM externe.
6. L'UI (`AIChatSheet` ou routes) s'affiche, permet d'interagir et valide le flux de bout en bout avec tests.
7. Zéro appel réel vers un LLM externe n'a été fait.

## 26. Implementation Order
1. Définition des types et interfaces (`types/ai.ts`).
2. Création des contrats Zod (Request/Response).
3. Implémentation du `ContextBuilder` (extraction des datas M01, M03, M04).
4. Implémentation de `MockAIProvider`.
5. Création des Server Actions d'orchestration (`sendChatMessage`).
6. UI : Création des composants de Chat contextuel et de la page `/dashboard/ai`.
7. Tests et intégration sans API.

### Réponses aux questions spécifiques (30.)
1. **Besoin d'une table `ai_sessions` ?** Oui, implémentée en M05 avec RLS strict.
2. **Besoin de `ai_messages` ?** Oui, implémentée en M05 avec RLS strict.
3. **Quantité de contexte ?** Strictement limité : Maximum 5 activités et 5 erreurs, filtrées par pertinence et par matière (`subjectId`).
4. **StudentLearningContext ?** Requêtes ciblées et filtrées renvoyant uniquement un sous-ensemble très pertinent formaté en condensé.
5. **PII ?** AUCUNE PII PAR DÉFAUT. Ni nom, ni prénom, ni UUID interne. Seules les données académiques et pédagogiques brutes sont transmises au modèle.
6. **Data vs Instructions ?** Les données sont traitées comme `UNTRUSTED DATA` par rapport aux instructions de confiance, même encapsulées en XML.
7. **Sources ?** Un tableau DTO dans la requête. M05 le laisse vide.
8. **Provenance ?** Distinction stricte : Source Provenance (`OFFICIAL | STUDENT | SYSTEM`) vs Generated By (`AI`).
9. **IA information ?** L'interface UI liera un badge de provenance visuel si la réponse s'appuie sur une source `OFFICIAL`. L'IA elle-même n'est jamais la source.
10. **OpenAI sans refactor ?** Grâce à l'interface `AIProvider`. `export class OpenAIProvider implements AIProvider { ... }`.
11. **M09/M10 sans refactor ?** M09 alimentera le paramètre `sourceContext` de l'`AIRequest` avant l'appel au Provider.
12. **Modes pédagogiques ?** Gérés par le System Prompt qui change selon la valeur de `request.mode`.
13. **Pas deux expériences ?** L'IA est un panel latéral contextuel (ChatSheet) accessible directement depuis l'exercice ou la matière courante.
14. **Coûts futurs ?** Minimisation absolue des prompts et caching de contextes très statiques.
15. **Rate limits ?** Middleware Next.js ou Server Action vérifiant le nombre de calls récents par `auth.uid()`.
16. **Persisté ?** Historique des chats (`ai_sessions`, `ai_messages`).
17. **Reconstruit ?** `StudentContext`, `AcademicContext` à chaque appel.
18. **Jamais envoyé ?** Mots de passe, email complet, UUIDs base de données inutiles.
19. **Context trop gros ?** Le `ContextBuilder` applique des limites déterministes (nombre d'éléments, taille tokens/caractères) et tronque le contexte **AVANT** l'appel au provider.
20. **Tester sans LLM ?** Un `MockAIProvider` reproduisant les modes et les contrats.
